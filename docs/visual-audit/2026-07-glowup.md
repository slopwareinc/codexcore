# CodexCore Glowup Audit — July 2026

**Historical engineering note.** Living findings log for the app-wide visual glowup
(Liquid Glass correctness, typography scale, spacing, theme architecture). Supersedes the
2025-07-06 audit in this directory where they disagree; that audit's structural verdict on
the theme still holds, and several of its findings remain open (noted inline).

Environment: macOS 26.5 (Darwin 25.5.0), `Package.swift` platform `.macOS(.v26)`, so
Liquid Glass is unconditionally available. `CodexAgentTheme.Effects.usesLiquidGlass`
exists to *opt out* (High Contrast preset), not to guard availability.

Authoritative API surface consulted (SDK, not docs — Apple's HIG pages are JS-rendered
and do not fetch):
`MacOSX.sdk/.../SwiftUICore.swiftmodule/arm64e-apple-macos.swiftinterface`

## 1. Liquid Glass

`codexGlass(_:tint:interactive:)` (`CodexTheme.swift:968`) is a sound wrapper with a
material fallback. The problems are in how it is used, and where it is absent.

### 1.1 Incorrect implementation

| # | Site | Problem |
|---|---|---|
| G1 | `CodexProjectSidebar.swift:118-125` | Stacks `.background { Rectangle().fill(.regularMaterial); Rectangle().fill(surface.opacity(0.22/0.34)) }` **and then** `.codexGlass(Rectangle(), tint:)`. Glass samples the opaque material stack instead of what is behind the window. Muddy, and defeats the effect. Also the only remaining `.regularMaterial` outside the fallback path. |
| G2 | `CodexChatWorkspace.swift:882-887` (`HeaderBubble`) | Real glass, then a manual `Capsule().stroke(border.opacity(0.4))` **and** a hardcoded `.shadow(.black.opacity(0.18), radius: 10, y: 4)`. Liquid Glass renders its own edge highlight and shadow; hand-drawn ones double up and read as fake. |
| G3 | Every `tint:` call site | `tint: theme.colors.surface.opacity(0.18 / 0.42)` (`CodexProjectSidebar:125`, `CodexChatWorkspace:884`, `CodexSettingsAboutRouteView:246`). Tinting glass with the near-black surface color turns it into smoked plastic. Tint is for *meaning* (accent for emphasis / selection), not for dimming. |
| G4 | whole codebase | **Zero `GlassEffectContainer`.** Adjacent glass elements each sample independently: they cannot merge or morph, and each costs its own pass. Header bubbles, composer chips, and the composer's accessory row are all groups that want one container. |
| G5 | whole codebase | **Zero `glassEffectID` / `glassEffectUnion` / `glassEffectTransition`.** No morphing between related glass shapes on state change. |
| G6 | whole codebase | **Zero `.buttonStyle(.glass)` / `.glassProminent`.** Every button is `.plain` plus a hand-rolled fill; ~40 sites. |
| G7 | `CodexTheme.swift:961-966` | `makeCodexGlass` only ever builds `.regular`. `.clear` is never used — correct for most chrome, but the composer/HUD over content is where `.clear` belongs. |
| G8 | `CodexTheme.swift:988` | `interactive:` defaults to `false` and is passed `true` at only 4 of 21 sites. Interactive glass is what gives controls their press response; every glass *control* should set it, and no glass *container* should. |
| G9 | fallback path (`CodexTheme.swift:991-995`) | Fallback stacks `.regularMaterial` **plus** an opaque `surfaceElevated.opacity(surfaceOpacity)` **plus** a stroke. For `highContrast` (`usesLiquidGlass: false`, `surfaceOpacity: 1`) the material is fully hidden behind the opaque fill, so it is dead work. |

## 2. Typography

**No scale exists outside the sidebar.** `Fonts` ships `body/chat/caption/label/code/micro`
plus a fully parameterised `SidebarTypography`. The sidebar is exemplary. Everything else
hand-picks a point size: **~100 raw `.font(.system(size:))` literals across 21 files**, at
30 / 28 / 26 / 24 / 22 / 18 / 17 / 16 / 15 / 14 / 13 / 12 / 11.5 / 11 / 10.

Consequence: **none of it responds to the user's UI font-size slider.** Only the sidebar
scales. `Fonts.scaled(baseTextSize:)` (`CodexTheme.swift:194`) exists and only feeds the six
generic tokens.

### 2.1 Landing-page typography (the headline complaint)

| # | Site | Literal |
|---|---|---|
| T1 | `Flows.swift:19` | 30pt semibold headline, `CodexBrandMark(size: 60)`, 24pt stack spacing, `CodexGlassPanel` 34pt padding + 28pt outer. A marketing hero, not app chrome. |
| T2 | `Flows.swift:75` | 28pt semibold + 60pt brand mark, same shape. |
| T3 | `CodexFlowComponents.swift:68` | 26pt bold monospaced device code with `tracking(3)`. |

| T5 | `CodexPluginRouteView.swift:454` | 24pt — the only 24 in a route title position. |

### 2.2 Competing tokens for one concept

- **Three route-title sizes coexist:** 22 (`CodexPluginRouteView:87`, `CodexMobileRouteView:30`, `CodexAutomationRouteView:46`, `CodexSettingsAboutRouteView:373`), 18 (`CodexPluginRouteView:300`, `CodexSettingsAboutRouteView:196`), 24 (`CodexPluginRouteView:454`).

- **Close-button glyph** is 11 bold (`CommandPalette:95`, `MCPStatusSheet:46`) vs 15 medium (`EditProjectSheet:615`).

- **Mono inline code** at 11.5 (`CodexPromptPanels:207,361`) distinct from `theme.fonts.code`.
- `.font(.title2)` (`CodexAgentPanels:350,568`) and `.font(.caption2)` — Apple semantics that ignore `uiFontSize`.

### 2.3 Missing

## 3. Spacing

`Spacing` contains no spacing ramp. It holds layout widths (`transcriptMaxWidth`,
`composerMaxWidth`, `sidePanelWidth`, `summaryPanelWidth`, `cardMaxWidth`,
`transcriptOuterMaxWidth`, `userBubbleMaxWidth`), a bar height, icon sizes
(`iconSmall/Medium/Large`), a line height (`chatLineSpacing`), one gap (`rowGap`), and one
inset (`chipPadding`). Three different concerns in one struct.

Consequently padding is ad-hoc everywhere: 34/28/24/20/18/14/12/11/10/8/7/6/5/4/3/2 as raw
literals. Radii too: hardcoded `cornerRadius: 12` (`EditProjectSheet` ×3) and
`cornerRadius: 10` (`CodexTranscriptViewV2:199`) alongside the `radii` tokens.

Missing: `xxs…xxl` ramp, `panelPadding`, `sheetPadding`, `rowPadding`, `sectionGap`.

## 4. Theme architecture

The reference for "multiple good themes" is Walkable's `ClayTheme.swift`
(`~/newprojects/experiments/walkable`). CodexCore is missing its four key ideas.

| # | Finding |
|---|---|
| A1 | **Presets are single-appearance.** `officialDark`, `midnight`, `warmMinimal`, `highContrast` are dark-only; `nativeLight` is light-only. Every one of the 23 colors is a fixed hex. Picking "Warm Minimal" in a light environment gives a dark window. A theme should be a *hue family* that resolves against light and dark — Walkable's `ClayColorPair { light, dark }`. |
| A2 | **`codexAdaptive(_:_:)` (`CodexTheme.swift:224`) is referenced zero times.** The one piece of adaptive infrastructure is dead. Per-view `.white`/`.black` ternaries reimplement it badly. |
| A3 | **`onAccent` is effectively hardcoded `.white`** across four of five presets. `warmMinimal.onAccent = 0x20130B` is correct; the rest assume a dark accent. No contrast derivation. Walkable solves this with `accentText` (a legible accent for text on the page) separate from `onAccent` (foreground on an accent fill). |
| A4 | **No `accentStrong` / `accentText`.** `accent` + `accentSoft` only, so pressed/hover accent states and accent-colored text share one value. |
| A5 | **Adaptive colors would silently break the AppKit transcript.** `CodexTranscriptRenderProjection.swift:292-311` converts 20 theme colors via `NSColor(theme.colors.x)`. That is safe *only* because every preset color is currently static. Making colors adaptive requires a resolved-palette hand-off (Walkable documents exactly this hazard) or the transcript resolves against the system appearance, not the window's. **Blocking prerequisite for A1.** |
| A6 | **No hover / pressed / selection / scrim tokens.** ~20 scattered opacities: sidebar row states at `0.50/0.36/0.22/0.18` (`CodexProjectSidebar:411-416, 540-545, 640-647`), palette rows at `0.34/0.18`, elevation tiers at `0.96/0.90/0.88/0.85/0.82/0.72/0.55/0.45/0.42/0.34/0.30/0.18/0.16/0.12/0.10`. |
| A7 | **`Effects.official` disagrees with itself.** `Animations.init` defaults `defaultDuration: 0.15` but `Animations.official` uses `0.25`; `Effects.official` omits `glassOpacity` (init default `0.72`) while `officialDark` sets it explicitly. Duplicate-default drift, carried over from the 2025 audit (C4-C6), still open. |
| A8 | **`highContrast` discards the theme rather than raising contrast of it.** Hardcoded black/white/yellow. It is also the only `usesLiquidGlass: false` preset, conflating "accessible" with "no glass" — `Reduce transparency` is a system setting and should drive that independently of preset choice. |
| A9 | **No `@Environment(\.accessibilityReduceTransparency)` anywhere.** Glass should degrade on that signal regardless of the chosen preset. `reduceMotion` is plumbed (via settings, not the system value); reduce-transparency is not plumbed at all. |
| A10 | `CodexDiffMarkerStyle` and `CodexDockIconVariant` carry `displayName` plumbing; verify they are rendered anywhere (2025 audit C8 flagged them as unused). |
| A11 | `CodexActivity.Kind.tint` / `.systemImage` defined but never read (pre-existing note). |

## 6. Verification constraint

The app builds and packages clean (`./scripts/package-app.sh`, signed) and launches. But
this session has **no Screen Recording permission**, so `screencapture` fails
(`could not create image from display`). Liquid Glass is composited by the window server
and does **not** render through `ImageRenderer`, `NSView.cacheDisplay`, or
`CALayer.render(in:)` — an app cannot capture its own glass without that permission.

Therefore:
- Typography, spacing, color, and layout are verified via the offscreen gallery harness,
  which renders faithfully.
- Glass is verified by API correctness against the SDK interface above, plus a build.
- Capturing real glass requires granting Screen Recording to the host terminal.

## 8. Post-glowup regression: appearance-frozen AppKit colors

Found from a live screenshot after the six glowup commits: a sidebar chat row
rendered as a solid near-black pill with barely-visible text in an otherwise
light window.

**Root cause.** `NSColor(someSwiftUIColor)` resolves an adaptive `Color`
against `NSAppearance.currentDrawing()`, which falls back to the *app's*
effective appearance when called outside an active draw pass — never the
window's or the view's own. Every theme color became adaptive in commit
`84f75ba` (dual-appearance themes). Two call sites converted theme colors to
`NSColor` from inside code that is not a draw pass, and both froze:

| Site | Where | Consequence |
| --- | --- | --- |
| `CodexProjectSidebar.swift` (`SidebarChatRowHost.update`) | Inside SwiftUI's `updateNSView`, colors pre-resolved once and handed to the row's `NSView` as static `NSColor` | The exact screenshot bug — a chat row frozen to the wrong appearance's hover/background color |
| `CodexFilePreviewView.swift` (`CodexCodeTextView.apply`) | Syntax-highlight foreground colors resolved once per content change | Same freeze, plus a second bug: the reapplication cache token didn't include appearance, so even a correct fix would never re-run on a live light/dark flip while a file preview was open |

The transcript's AppKit theme (`CodexTranscriptRenderProjection`) had already
been fixed for this exact hazard while making themes dual-appearance, but the
fix wasn't generalized or swept to the rest of the codebase — these two sites
were introduced or exposed by the same commit and missed.

**Fix.** Extracted the transcript's ad hoc fix into `CodexAppKitColor.resolve`
(`CodexAppKitColorResolution.swift`), which pins resolution inside
`NSAppearance.performAsCurrentDrawingAppearance` — the only API that resolves a
dynamic color against a specific appearance regardless of when or where it
runs. `NSAppearance.codexResolve(_:)` reads better at call sites that already
have a live `effectiveAppearance`.

- Sidebar row: `configure` now takes SwiftUI `Color`s, not `NSColor`, and
  resolves them lazily inside `updateChrome()` against the view's own
  `effectiveAppearance` — so it's correct regardless of when `configure` ran,
  and a `viewDidChangeEffectiveAppearance` override repaints on a live flip.
- File preview: same resolution fix, plus the cache token now includes the
  resolved appearance name, so a pure light/dark flip with unchanged text
  correctly forces recoloring.
- The transcript's own resolver now delegates to the shared implementation
  instead of duplicating the logic.

**Full sweep performed** (not just the two found sites) — every `NSColor(`,
`.cgColor` assignment, `NSViewRepresentable`, and `NSView`/`NSTextView`
subclass in `Sources/` was traced to confirm nothing else converts an adaptive
`Color` outside a draw pass or a value already resolved through
`CodexAppKitColor`. Confirmed clean: `CodexTranscriptCollectionCell` (colors
come pre-resolved via `CodexTranscriptAppKitTheme`), `CodexTranscriptTurnMinimap`
(same), `CodexTerminalToolView` (already threads `colorScheme` explicitly with
an `onChange` hook), `ANSITerminalStyle` (deliberately fixed brand RGB, not
theme-adaptive), `CodexVoiceOrb`'s white/black literals (deliberate
appearance-invariant decoration, not chrome). No `NSWindow.appearance`
overrides exist anywhere — appearance is set exactly once, via
`.preferredColorScheme` at both window roots, so there is nothing else that
could fight it.

**Regression tests**, both proven to fail against the pre-fix code before being
verified to pass against the fix:

- `CodexAppKitColorResolutionTests` (5 tests) — resolves colors while the
  *ambient* process appearance is deliberately wrong, asserts the result
  matches the requested appearance anyway.
- `CodexSidebarHoverPerformanceTests.hoverColorMatchesTheViewsOwnAppearanceNotTheAmbientOne`
  — pins a real `NSWindow` to Light while the ambient appearance is Dark,
  asserts the painted hover color is Light.

Committed as `feat(ui): resolve AppKit colors against the view's own appearance`.
